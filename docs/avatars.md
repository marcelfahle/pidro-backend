# Profile avatars (PID-76)

Avatars are owned by the user row and available to guest and registered accounts. Guest upgrades retain the same user id and avatar; account deletion cascades to `user_avatars`. Only the normalized 256×256 JPEG is stored in PostgreSQL—never the upload or its metadata.

Uploads use multipart field `avatar`. The request parser is bounded just above 5 MiB for multipart framing and the file itself is limited to 5 MiB. JPEG and PNG are decoded by ImageMagick with 64 MiB memory, 128 MiB map, 256 MiB disk and one thread; input is limited to 16 MP and 8192 pixels per side. EXIF orientation is applied, metadata stripped, a centered square thumbnail produced, and output must be at most 64 KiB. HEIC is intentionally unsupported; clients convert it natively. Processing completes before the atomic upsert, so failures preserve the prior image.

The lowercase SHA-256 of normalized bytes is the immutable URL version. Public reads require an exact version, return no stale bytes, and cache successes for one hour. After a committed upload/removal, `RoomManager.identity_changed/1` publishes on an internal PubSub topic subscribed by each node's RoomManager. Each node re-emits its affected room snapshots; lobby subscribers freshly load avatar metadata without mutating room lifecycle state. Normal user/room joins select only version metadata, never image bytes.

`POST /api/v1/profile/avatar` and `DELETE /api/v1/profile/avatar` derive ownership from authentication and return `{data: {avatar_url}}`. `GET /api/v1/users/:user_id/avatar/:version` is public: anyone holding the URL can view it. Removing an avatar stops origin delivery; already downloaded or cached copies cannot be revoked and may remain fresh for one hour. Replaced versions return 404 at the origin.

Processing is limited to one conversion per node, with a fail-fast 503 retry response when busy; identify and convert both have resource/time limits. Upload rate limiting applies per authenticated user. Originals are Plug-managed temporary uploads and normalization outputs are removed in `after`, including failures. Replacements overwrite the previous database bytes atomically and user deletion (including guest reaping) cascades the row, so no orphan asset cleanup job is needed. Cluster refresh requires working inter-node Phoenix PubSub; the database remains authoritative on reconnect/refetch.
