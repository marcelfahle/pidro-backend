# Research: PID-49 Veteran level (XP) + Heritage

## Summary

Everything PID-49 needs to land already exists as scaffolding:

- The completion path persists, per finished room, a `final_scores` map
  (`%{north_south: int, east_west: int}`), a `winner` team atom, and a
  `player_results` map (`%{user_id => %{participation, result, team, position}}`).
  From these three, per human participant you can compute **their team's final
  score** (`final_scores[result.team]`) and **whether their team won**
  (`result.result == :win`). This is enough for the XP award (score-for-both +
  win-bonus-for-winner).
- The completion-update seam is `Profiles.apply_completed_game/3`
  (`profiles.ex:141`), called once per room inside the `save_completed_game/4`
  transaction (`stats.ex:326`). It has TWO bands today: (1) a **counters loop over
  ALL valid-UUID participants** (`profiles.ex:144-152`) and (2) a **rating block
  gated to rated 4-human games only** (`apply_live_rating/2`, `profiles.ex:155`).
  **XP belongs with band (1)** — every completed game, NOT gated by
  `rated_game?/1`, so single-player and bot-filled games still pay XP. The
  rebuild equivalent is `rebuild_from_history/1` (`profiles.ex:171`), an
  order-agnostic recompute that XP can mirror (XP is a simple per-game sum, so it
  is order-independent like the counters).
- Profile columns ship with defaults: `veteran_level :integer default: 0`,
  `veteran_xp :integer default: 0`, `heritage_flags :map default: %{}`
  (`player_profile.ex:36-46`); all three are already in `@castable`
  (`player_profile.ex:51-66`) so the existing `changeset/2` casts them.
- **A real Pidro 1 XP/level curve WAS FOUND** in the legacy backend
  `/Users/mf/code/pidro/pidro_api` (outside the worktree). XP award:
  **winner = team final score + 50 flat bonus; loser = team final score** (no
  bonus). The 1–100 level is a precomputed 199-entry threshold array generated by
  `points += floor(lvl + 300 * 2^(lvl/7))`, then `floor(points/4)` cumulative;
  `level = count(thresholds <= xp) + 1`. **Pidro game target score = 62**
  (`gamestate.ex:117`), 14 points available per hand, bids 6–14 — so a typical
  end-of-game team score is roughly 30–62, giving ~30–112 XP/game.

## 1. Completion data shape for XP

### `final_scores` (the `scores` argument)

- Stored as `GameStats.final_scores :map` (`game_stats.ex:15`). Written verbatim
  from the `scores` argument of `save_completed_game/4` (`stats.ex:299, 313`).
- Shape: **per-team cumulative score map keyed by team atom**:
  `%{north_south: 62, east_west: 45}` (atom-keyed when written in-memory;
  JSONB round-trips to string keys `%{"north_south" => 62, ...}` on read).
  Confirmed by PID-44 doc (`PID-44-player-profile-store.md:63`), PID-46 doc
  (`PID-46-rerating-job.md:63`), and the integration test fixture
  `%{north_south: 62, east_west: 45}` (PID-47 doc, `profile_rollup_test.exs`).
- Values are integers (cumulative team scores at game over). Game target =
  `winning_score: 62` (`apps/pidro_engine/lib/pidro/core/gamestate.ex:117`); the
  engine's running totals live in
  `cumulative_scores: %{north_south: 0, east_west: 0}` (`gamestate.ex:111`).

### `winner`

- `GameStats.winner :string`, validated to `["north_south", "east_west"]`
  (`game_stats.ex:43`). Passed in as an atom (`:north_south`) and normalized to a
  string by `GameStats.changeset` (`game_stats.ex:51-67`). In-memory at the seam
  it is still the atom.

### `player_results`

- Built by `Stats.build_player_results/3` (`stats.ex:239-257`) from the room's
  seats. `%{user_id => %{participation, result, team, position}}`
  (`build_result/3`, `stats.ex:406-416`):
  - `position` — `:north | :east | :south | :west`
  - `team` — `team_for_position(position)`: north/south → `:north_south`,
    east/west → `:east_west` (`stats.ex:453-454`)
  - `result` — `:win` if `team == winner`, else `:loss` (`stats.ex:407-408`)
  - `participation` — `:played | :substitute | :abandoned` (pure bots are
    `:skip`ped and never appear — `classify_seat/1`, `stats.ex:383-404`)
- Persisted as `GameStats.player_results :map` (JSONB); string-keyed after a DB
  round-trip. Helpers in both `stats.ex` and `profiles.ex` tolerate atom OR
  string keys (e.g. `win_from_result?/1`, `profiles.ex:579-583`).

### Computing per-human XP

For each entry `{user_id, result}` in `player_results` where `user_id` casts to a
valid UUID (`Ecto.UUID.cast/1`, as the counters loop already does):

1. **Team final score** = `final_scores[result.team]` (handle atom/string key:
   `result.team` is `:north_south`; the score map may be string-keyed after JSONB).
2. **Won?** = `result.result == :win` (or `"win"` from JSONB). Equivalently
   `result.team == winner`.
3. **XP for this game** = `team_score + (if won?, do: win_bonus, else: 0)` plus an
   optional configurable extra-bonus lever (events/streaks).

This must run for EVERY participant of EVERY completed game (incl. single-player
and bot-filled), so it sits in the same loop as the lifetime counters, NOT behind
`rated_game?/1`. Bots already never appear in `player_results`; only real human
UUIDs (incl. `:abandoned`/`:substitute`) get XP, matching the counters' policy.

## 2. The completion-update seam + rebuild

### Live seam — `Profiles.apply_completed_game/3` (`profiles.ex:141-158`)

```elixir
@spec apply_completed_game(map(), atom() | String.t(), keyword()) :: :ok
def apply_completed_game(player_results, winner, _opts) when is_map(player_results) do
  # 1. Lifetime counters (PID-44): bump every valid-UUID participant.
  Enum.each(player_results, fn {user_id, result} ->
    case Ecto.UUID.cast(user_id) do
      {:ok, valid_id} ->
        apply_one(valid_id, win_from_result?(result))

      :error ->
        Logger.warning("Profiles.apply_completed_game skipping non-UUID id #{inspect(user_id)}")
    end
  end)

  # 2. Ratings (PID-47): rated 4-human games only, priors from stored rows.
  apply_live_rating(player_results, winner)

  :ok
end
```

- **Where XP slots:** with band (1), the per-participant loop — XP accrues for
  **every completed game**, exactly like `games_played`/`wins`/`losses`. It is
  NOT behind `apply_live_rating/2` (which IS gated by `rated_game?/1`,
  `profiles.ex:458-473`). PID-47's `apply_live_rating/2` deliberately rates only
  4-distinct-human 2v2 games; XP must NOT inherit that gate (ticket: "dedication
  XP accrues in single-player too; skill rating does NOT").
- The XP award needs `final_scores`/`scores` too (to read the team score). The
  `/3` seam currently receives only `(player_results, winner, opts)` — `scores`
  is in scope at the call site (`stats.ex:326`, var `scores`) but is NOT passed
  in. PID-49 either (a) reads `result.team` against a scores arg threaded through,
  or (b) computes per-team score some other way. Note `player_results` itself does
  NOT carry the numeric score — only `team`/`result`/`position`. So PID-49 must
  thread `scores`/`final_scores` into the seam (a signature change) OR re-read the
  just-inserted `GameStats.final_scores`. The cleanest mirror of the existing
  style is to extend `apply_completed_game` to also accept the scores map.

`apply_one/2` (`profiles.ex:561-575`) is the counter writer — `get_or_create_profile`
(lazy create, race-safe) then `Repo.update_all(inc: [...])`. An XP writer would be
an analogous `Repo.update_all(inc: [veteran_xp: delta])` then recompute
`veteran_level` from the curve (level is derived from cumulative xp, so it can be
written alongside, or computed at read time — see Open Questions).

### Rebuild — `rebuild_from_history/1` (`profiles.ex:171-189`) / `rebuild_all/0`

```elixir
def rebuild_from_history(user_id) do
  games =
    from(gs in GameStats, where: ^user_id in gs.player_ids)
    |> Repo.all()

  games_played = length(games)
  wins = Enum.count(games, &won_game?(&1, user_id))
  losses = games_played - wins

  with {:ok, profile} <- get_or_create_profile(user_id) do
    profile
    |> PlayerProfile.changeset(%{
      games_played: games_played,
      wins: wins,
      losses: losses
    })
    |> Repo.update()
  end
end
```

- **Order-agnostic counter rebuild**: collects all of a user's `game_stats`,
  counts, overwrites. **XP rebuilds the same way**: XP is a per-game sum
  (`team_score + win_bonus`), so total XP = `Enum.reduce` over the user's games of
  `xp_for_game(game, user_id)`, and `veteran_level` = curve lookup of that sum.
  Add `veteran_xp`/`veteran_level` to the changeset map here, exactly like the
  three counters. This is order-independent (sum is commutative), unlike ratings
  whose rebuild needs the totally-ordered `rerate_all/0` (`profiles.ex:270`).
- `rebuild_all/0` (`profiles.ex:198-208`) collects the distinct user-id set from
  `game_stats.player_ids` and calls `rebuild_from_history/1` per user — XP rides
  along for free once it is in `rebuild_from_history/1`.
- `won_game?/2` (`profiles.ex:589-609`) already reads the stored result (with
  position-vs-winner fallback for legacy rows) — the same helper an XP rebuild
  reuses to decide the win bonus. To read the team score it additionally needs
  `game.final_scores` + the user's `team` (derivable from `player_results` or the
  `player_ids` index → position → team, as `get_player_position/2` does at
  `profiles.ex:618-628`).
- `rerate_all/0` / `rerate_incremental/0` are RATING-only (the totally-ordered
  replay needed because each rating update depends on priors). XP does not need
  them — it has no ordering dependency.

## 4. Config conventions (recap from PID-48)

The established pattern (both `PidroServer.Rating.Tier` and
`PidroServer.Games.Lifecycle`):

- A pure module owns a `@defaults` map and a private `config/1` reader:

  ```elixir
  defp config(key) when is_map_key(@defaults, key) do
    app_config = Application.get_env(:pidro_server, __MODULE__, [])
    Keyword.get(app_config, key, Map.fetch!(@defaults, key))
  end
  ```
  (`tier.ex:126-129`, identical shape in `lifecycle.ex:66-69`.)
- A public `defaults/0` returns the whole map (`tier.ex:105-106`,
  `lifecycle.ex:74-75`).
- Config is keyed by the module under `:pidro_server` in `config/config.exs`:

  ```elixir
  config :pidro_server, PidroServer.Rating.Tier,
    provisional_min_games: 10,
    ...
    master_min: 34.0
  ```
  (`config/config.exs:47-54`; Lifecycle at `:25-41`.) `config/runtime.exs:58-59`
  shows the prod env-var override merge pattern; `config/test.exs:39` overrides per
  test env.

**Where PID-49 config lives:** a new
`config :pidro_server, PidroServer.Progression` (or `.Veteran`) block holding:
- the **win bonus** (legacy = `50`),
- the **extra-bonus lever** (events/streaks; default `0`),
- the **level thresholds / XP curve** — either the explicit 199-entry array, or
  the generator params (`base`, `growth`, `divisor`) so the curve is regenerable,
- the **milestone titles** (named level→title map).

Following Tier, the `PidroServer.Progression`/`Veteran` module holds `@defaults`
(curve params + bonuses) and a `config/1` reader; titles can be a module attribute
list or a config key.

## 5. Pidro 1 XP/level curve + scoring findings

### Game scoring / target (worktree, for calibration)

- **Target score to win = 62** (`apps/pidro_engine/lib/pidro/core/gamestate.ex:117`,
  `config.winning_score: 62`; documented at `gamestate.ex:44`).
- **14 points available per hand** (`apps/pidro_engine/lib/pidro_engine.ex:107`,
  "Point Cards (14 points total)").
- **Bids 6–14** (`gamestate.ex:116`, `game_stats.ex:47` validates bid 6..14).
- Running team totals: `cumulative_scores: %{north_south, east_west}`
  (`gamestate.ex:111`); these become `final_scores` at game over.
- Implication for the curve: an end-of-game **team score** typically lands ~30–62
  (winner near 62; loser anywhere from negative — `allow_negative_scores: true`,
  `gamestate.ex:120` — up to ~50). So per-game XP ≈ **30–112** (loser score, or
  winner score + bonus).

### Legacy Pidro 1 XP award (FOUND — outside worktree)

`/Users/mf/code/pidro/pidro_api/lib/pidro_api/game_results.ex:185-211`
(`update_all_users/6`):

```elixir
winner_xp = winner_data[:Score] + 50   # team final score + flat 50 win bonus
runner_xp = runner_data[:Score]        # team final score, NO bonus
...
xp = cond do
  is_winner -> winner_xp
  is_runner -> runner_xp
  true -> 0
end
```

- **Both teams earn XP = their team's final game score; winners additionally get a
  flat +50 bonus.** Confirmed by tests
  (`pidro_api/test/features/game_results_test.exs:156-160, 446-451`): winner
  `66 + 50 = 116`, loser `54`. This is exactly the ticket's "end-of-game score as
  XP for BOTH teams + a win bonus for winners (anti-rage-quit)". XP is per-player,
  stored on `users.xp` and as `xpoints` rows (`x_point.ex`, `xp :integer`).
- The +50 is a hard-coded literal (the **win bonus** PID-49 should make
  configurable); there is no "extra bonus" lever in legacy — that is a new PID-49
  addition.

### Legacy 1–100 level curve (FOUND)

`/Users/mf/code/pidro/pidro_api/lib/pidro_api_web/views/user_view.ex:378-403` +
`all_levels/0` (`:405` onward):

```elixir
def user_level(nil), do: 1
def user_level(xp) do
  user_levels = Enum.filter(all_levels(), fn p -> xp >= p end)
  Enum.count(user_levels) + 1            # level = (# thresholds passed) + 1
end

defp all_levels do
  # JS: for (lvl=1; lvl<=max; lvl++) { points += Math.floor(lvl + 300 * Math.pow(2, lvl/7));
  #     if (lvl >= min) { a.push(Math.floor(points/4)); } }
  [83, 174, 276, 388, 512, 650, 801, 969, 1154, 1358, ...,  # 199 entries
   ..., 287_416_243_706, 317_333_260_352]
end
```

- **Curve generator** (from the JS comment, the source of truth): a cumulative sum
  where each level's increment is `floor(lvl + 300 * 2^(lvl/7))`, and each stored
  threshold is `floor(cumulative_points / 4)`. The array is the precomputed
  prefix-sums. **199 thresholds** are present (so the array supports ~200 levels,
  far beyond the "1–100" the ticket references — PID-49 can truncate/keep as
  needed).
- **Level derivation**: `level = count(thresholds where threshold <= xp) + 1`. So
  level 1 = `xp < 83`, level 2 = `83 <= xp < 174`, etc. First thresholds:
  `83, 174, 276, 388, 512, 650, 801, 969, 1154, 1358, 1584, 1833, 2107, ...`.
- Companion helpers (for the post-game/profile UI): `next_level_at/1`,
  `next_level_in/1`, `level_progress/1` (`user_view.ex:385-403`) — the
  "progress to next level" math PID-52's summary may reuse.
- It is consumed by the live profile API today
  (`pidro_api/.../user_controller.ex:1059-1064`,
  `current_level`/`level_progress`) and the website
  (`pidro-site2/app/(authenticated)/profile/page.tsx:218-221`,
  "Level {profile.current_level}").

## 6. Pure module + test conventions (recap)

For a `PidroServer.Progression` (or `PidroServer.Veteran`) pure module, follow
`PidroServer.Rating.Tier` (`tier.ex`) and `PidroServer.Rating` (`rating.ex`):

- **Pure, no DB.** Module-level `@moduledoc` stating it is a pure mapping (XP →
  level + milestone title; game result → XP delta). All thresholds/bonuses
  config-tunable via the `@defaults` + private `config/1` pattern (§4), with a
  public `defaults/0`.
- **Doctests in `@doc`**, exercised via `doctest PidroServer.Progression` in the
  test module (`tier_test.exs:8`; `rating_test.exs` similarly). E.g.
  `iex> Progression.level_for(83) \n 2`.
- **Typespecs** on public functions (`@type`, `@spec`) as in `tier.ex:29-34, 65`
  and `rating.ex:16-17`.
- **Test file** `apps/pidro_server/test/pidro_server/progression_test.exs` (mirror
  `apps/pidro_server/test/pidro_server/rating/tier_test.exs`). Use
  `use ExUnit.Case, async: false` for any test that mutates `Application.put_env`
  to assert config overrides are respected (the comment at `tier_test.exs:2-4`
  explains the async:false rationale); pure-math tests can be `async: true`.
- **Boundary tests** around each threshold (just below / at / just above), a
  `defaults/0` assertion (`tier_test.exs:33-43`), and config-override tests.
- **Completion-seam integration tests**: extend
  `apps/pidro_server/test/pidro_server/stats/profile_rollup_test.exs` (drive a real
  `{:game_over, ...}` through `RoomManager`, poll for the `GameStats` row, assert
  `veteran_xp`/`veteran_level` moved for ALL participants — including a
  single-player/bot game where ratings stay put but XP still accrues). The
  "live == rebuild" assertion mirrors PID-46/47: run completions, then
  `rebuild_all/0`, assert XP/level identical.

## Open Questions

1. **Threading `scores` into the seam.** `apply_completed_game/3` does not receive
   `final_scores` today (only `player_results` + `winner`). PID-49 must thread the
   scores map into the seam (signature change) OR re-read the just-inserted
   `GameStats.final_scores` inside the transaction. `player_results` carries
   `team`/`result` but NOT the numeric team score. Which approach?
2. **`veteran_level` default 0 vs legacy level 1.** The column defaults to `0`;
   legacy `user_level(nil) = 1` and the curve makes `xp < 83` ⇒ level 1. Does
   PID-49 keep 0 as "no games / pre-level-1", or align to start at level 1?
3. **Store level or derive at read time?** Tiers (PID-48) derive at read time from
   stored μ/σ. XP-level could likewise be a pure `Progression.level_for(xp)` call
   in `get_profile_for_screen/1`, leaving `veteran_level` as a denormalized cache
   (written by the completion path / rebuild) — or as the single source. Which?
4. **Curve representation in config.** Store the explicit 199-entry threshold array
   (verbatim from legacy, exact carry-over) or the generator params
   (`floor(lvl + 300*2^(lvl/7))`, `/4`) and compute? Array = exact parity; params =
   compact + extensible. The ticket wants "thresholds + bonus in config."
5. **Milestone titles.** The ticket wants "named milestone titles" mapped to
   levels. No legacy title set was found in `pidro_api` (levels are numeric only) —
   titles appear to be NEW. Where does the canonical title list come from
   (design/brainstorm doc not in this worktree —
   `docs/brainstorms/2026-06-05-progression-and-ranking-requirements.md` is
   referenced by memory but ABSENT here)?
6. **Heritage flag vocabulary.** `heritage_flags` is free-form JSONB. The ticket
   names "played Pidro 1, founding ribbon, legacy accolades" — what is the exact
   key set / shape PID-49 models, and who writes them (PID-49 vs the PID-53
   carry-over migration)?
7. **Extra-bonus lever semantics.** "backend-configurable extra bonus for
   events/streaks" — is it a flat per-game add, a multiplier, or a streak-aware
   function? Streaks would need state not currently on the profile (no streak
   counter column exists).
8. **Single-player XP and `:abandoned`/`:substitute`.** Counters already credit
   `:abandoned`/`:substitute` participants. Does XP credit a player whose seat was
   abandoned (bot finished under their UUID)? The ticket says XP accrues in
   single-player; confirm it also accrues for abandoned/substitute the same way
   counters do.
