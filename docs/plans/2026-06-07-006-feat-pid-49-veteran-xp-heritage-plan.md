# feat: Veteran level (XP-driven) + Heritage

## Overview

PID-44 shipped the `player_profiles` row with veteran/heritage columns at
defaults (`veteran_level :integer 0`, `veteran_xp :integer 0`,
`heritage_flags :map %{}`), already cast by `PlayerProfile.changeset/2` and
already surfaced (raw) by `Profiles.get_profile_for_screen/1`. PID-47 wired the
live completion seam (`Profiles.apply_completed_game/3`) and an order-agnostic
`rebuild_from_history/1`. PID-49 makes the veteran columns *live*:

- **XP accrues on every completed game** — winners AND losers, including
  single-player and bot-filled games. XP is *dedication*, not skill: it is NOT
  gated by `rated_game?/1` (that gate stays exclusive to the rating block).
- **Level is derived from an XP curve** faithfully recovered from Pidro 1: a
  cumulative threshold list `floor(lvl + 300 * 2^(lvl/7))` then `÷4`;
  `level = count(thresholds <= xp) + 1`, capped at `max_level` (100). Keeping
  the legacy curve as the default guarantees imported XP (PID-53) lands on the
  same level it did in Pidro 1.
- **Continuous level + milestone titles**: every level is a number; named
  titles are a config level→title map ("highest title whose level ≤ current").
- **Heritage is modelled + displayable**: `heritage_flags` gets a defined key
  vocabulary and a pure display helper. PID-49 models and displays only;
  defaults stay empty. PID-53 (migration) populates them.

The work is one pure, doctested module `PidroServer.Progression` (the XP/level/
title math + a `Heritage` display helper), a config block, a small completion-
seam signature change to thread the per-team `scores` map through, an extension
to `rebuild_from_history/1`, and derived fields added to
`get_profile_for_screen/1`. Follows `apps/pidro_server/CLAUDE.md`: pure logic in
a pure module, single source of truth, thin wiring.

### Legacy source of truth (cited in the moduledoc)

Recovered from the Pidro 1 backend (outside this worktree):

- **XP award** — `pidro_api/lib/pidro_api/game_results.ex:185-211`: winner XP =
  team final score + 50 flat bonus; loser XP = team final score (no bonus).
  Confirmed by `pidro_api/test/features/game_results_test.exs:156-160` (winner
  `66+50=116`, loser `54`).
- **Level curve** — `pidro_api/lib/pidro_api_web/views/user_view.ex:378-405`:
  `user_level(xp) = count(all_levels ≤ xp) + 1`; `all_levels` is the precomputed
  prefix-sum array generated by `points += floor(lvl + 300*2^(lvl/7))` then each
  stored threshold `= floor(points/4)`. First thresholds:
  `83, 174, 276, 388, 512, 650, 801, 969, 1154, 1358, …`.

## Non-Goals (explicit — owned elsewhere)

- **Legacy XP / level / heritage import** — **PID-53**. PID-49 builds the engine
  and models the flags; it never reads Pidro 1 data or writes heritage values
  (defaults stay empty).
- **Post-game "what changed" / level-up celebration payload** — **PID-52**. No
  before/after delta, no "you levelled up" event. (XP-to-next-level *progress*
  may appear in `get_profile_for_screen/1` as a cheap derived read; that is a
  static snapshot, not a delta.)
- **Achievements / badges** — **PID-50**.
- **Skill tier (μ/σ → tier)** — **PID-48** (done) and its API exposure **PID-54**.
- **Stateful streaks.** The `extra_bonus` lever is a flat, config/opts-supplied
  per-game add. No streak counter, no order-dependent bonus — base XP stays a
  commutative per-game sum so the rebuild is exact. Streaks are deferred.

## Decisions (decided + justified)

1. **Curve stored as generated module attribute, config-tunable params.**
   The default 100-entry threshold list is computed **once at compile time** into
   a `@legacy_thresholds` module attribute from the legacy generator params
   (`base_growth: 300`, `growth_divisor: 7`, `point_divisor: 4`). This is the
   pragmatic middle: the array is exact legacy parity (so PID-53 imports land on
   the same level), yet it is regenerable and the params are config knobs rather
   than a 100-element literal pasted into config. A fully config-supplied
   explicit list is also honoured — if `:thresholds` is set in config it wins
   verbatim. Decision: **generated default attribute; `:thresholds` config
   override optional; generator params tunable.**

2. **`veteran_level` is a denormalized cache; XP is the source of truth.**
   The completion path and rebuild both write `veteran_level = level_for_xp(xp)`
   alongside `veteran_xp`, so the stored level is always coherent with stored XP
   (a single per-game sum makes this trivial and order-agnostic). Tiers (PID-48)
   derive at read time because μ/σ replay is ordered; XP has no such constraint,
   and persisting the level keeps leaderboard/admin queries cheap. The level is
   *also* recomputed (defensively, from `veteran_xp`) in
   `get_profile_for_screen/1` so a stale cache can never surface — they are
   equal by construction. Decision: **persist both; treat XP as canonical.**

3. **Level starts at 1, not 0.** Legacy `user_level(nil) = 1` and the curve makes
   `xp < 83 ⇒ level 1`. The column default `0` means "never written"; the moment
   any game is applied (or rebuild runs), level becomes `≥ 1`. `level_for_xp(0)`
   returns `1`. `get_profile_for_screen/1` returns `max(stored_level, 1)`-by-
   construction (it recomputes from XP, so an untouched `0` profile reports
   level `1`). Decision: **levels are 1..max_level; 0 is "unwritten" only.**

4. **Thread `scores` into the seam (signature change), do not re-read the row.**
   `player_results` carries `team`/`result` but not the numeric team score; the
   `scores` map (`%{north_south: int, east_west: int}`) is already in scope at
   the `stats.ex:326` call site (it is the `scores` argument of
   `save_completed_game/4`). Passing it in is cleaner and cheaper than
   re-`SELECT`ing the just-inserted `GameStats.final_scores` inside the same
   transaction. Decision: **add `scores` to `apply_completed_game`; pass it from
   the call site.**

5. **XP credits the same participants the counters do.** Every valid-UUID key in
   `player_results` (including `:abandoned` / `:substitute`) gets XP, exactly
   like `games_played`/`wins`/`losses`. Bots never appear (the caller skips
   them). This matches the ticket ("dedication XP in single-player too").

```elixir
defmodule PidroServer.Progression.Heritage do
  @moduledoc """
  Pure modelling + display of origin-recognition flags stored in
  `player_profiles.heritage_flags` (free-form JSONB, default `%{}`).

  PID-49 defines the known key vocabulary and turns the flags map into a
  structured, displayable list. PID-49 NEVER writes these (defaults stay empty);
  PID-53 (account migration) populates them on import.

  ## Known keys

    * `played_pidro_one :: boolean`   — had a Pidro 1 account
    * `founding_member  :: boolean`   — pre-launch / founding cohort
    * `legacy_level     :: integer`   — the carried Pidro 1 level (display only)
    * `legacy_accolades :: [string]`  — named legacy awards/titles

  Tolerates atom- or string-keyed maps (JSONB round-trips to string keys).
  """

  @type flags :: map()
  @type badge :: %{key: atom(), label: String.t(), value: term()}

  @doc """
  Turns a `heritage_flags` map into an ordered list of displayable badges,
  skipping falsy / absent flags. Returns `[]` for an empty/nil map.
  """
  @spec display(flags() | nil) :: [badge()]
  def display(flags)
end
```

Design notes:

- **Pure, no DB, deterministic, doctested**, mirroring `Rating.Tier`.
- `xp_for_game/3` clamps to `non_neg_integer()` (legacy `allow_negative_scores`
  means a loser team score *can* be negative; XP must never go below 0).
- `level_for_xp/1` uses the same `count(thresholds <= xp) + 1` derivation as
  legacy, then `min(_, max_level)`.
- `title_for_level/1` reads the config `titles` map (`%{level => title}`),
  returns the title of the highest key `≤ level`; if no key `≤ level` (i.e.
  level below the lowest configured), returns the lowest title.
- `display/1` keeps the badge order stable (vocabulary order), tolerates
  string keys, and emits `legacy_level`/`legacy_accolades` only when present.

## Algorithm — the curve

```
# Generator (legacy, source of truth). lvl runs 1..max_level.
build_thresholds(max_level, base_growth, growth_divisor, point_divisor):
  {thresholds, _points} =
    Enum.reduce(1..max_level, {[], 0}, fn lvl, {acc, points} ->
      points = points + floor(lvl + base_growth * :math.pow(2, lvl / growth_divisor))
      {[floor(points / point_divisor) | acc], points}
    end)
  Enum.reverse(thresholds)            # ascending: [83, 174, 276, 388, 512, ...]

# Level derivation (legacy).
level_for_xp(xp):
  level = Enum.count(thresholds, &(&1 <= xp)) + 1
  min(level, max_level)
```

- Default `max_level = 100` ⇒ a 100-entry ascending threshold list computed
  once into `@legacy_thresholds` (module attribute, compile-time). The legacy
  array had 199 entries supporting ~200 levels; we cap the *default* at 100 per
  the ticket, but `max_level` is a config knob.
- `level_for_xp(0) = count([]≤0)+1 = 1`. `level_for_xp(83) = 2`
  (one threshold `83 ≤ 83`). `level_for_xp(very_large) = max_level` (cap).
- `next_level_at(xp)` = first threshold strictly `> xp`, or `:max` at the cap.
- `level_progress(xp)` = `{xp - lower_threshold, upper_threshold - lower_threshold}`
  where `lower_threshold` is the current level's start (0 for level 1) and
  `upper` is `next_level_at(xp)`; `:max` at the cap.

### XP award

```
xp_for_game(team_score, won?, opts):
  win_bonus   = opts[:win_bonus]   || config(:win_bonus)    # default 50 (legacy)
  extra_bonus = opts[:extra_bonus] || config(:extra_bonus)  # default 0
  raw = team_score + (if won?, do: win_bonus, else: 0) + extra_bonus
  max(raw, 0)
```

- `win_bonus` default `50` is the proven Pidro 1 value.
- `extra_bonus` default `0` is the events lever — a flat per-game add supplied
  by config or per-call `opts`. No state. Streaks deferred (keeps base XP
  order-agnostic and rebuildable).

## Completion-seam change (all games)

### Signature

`Profiles.apply_completed_game` gains the per-team `scores` map. The arity-2
shim stays for back-compat; a new arity-2 default for `scores` keeps existing
`/3` callers working too (none pass scores today).

```elixir
# OLD: apply_completed_game(player_results, winner, opts \\ [])
# NEW:
@spec apply_completed_game(map(), atom() | String.t(), map(), keyword()) :: :ok
def apply_completed_game(player_results, winner, scores \\ %{}, opts \\ [])
def apply_completed_game(player_results, winner, scores, _opts)
    when is_map(player_results) do
  Enum.each(player_results, fn {user_id, result} ->
    case Ecto.UUID.cast(user_id) do
      {:ok, valid_id} ->
        apply_one(valid_id, win_from_result?(result))          # PID-44 counters
        apply_xp(valid_id, result, scores)                     # PID-49 XP (NEW)
      :error ->
        Logger.warning("... skipping non-UUID id #{inspect(user_id)}")
    end
  end)

  apply_live_rating(player_results, winner)                    # PID-47 (gated)
  :ok
end

def apply_completed_game(_player_results, _winner, _scores, _opts), do: :ok
```

The arity-2 `apply_completed_game/2` shim delegates with `%{}` scores + `[]`
opts (it is the PID-44 historical shape; with empty scores XP for those callers
is `0 + bonus` — but in practice the only production caller is `stats.ex`, which
will pass real scores).

New private writer (mirrors `apply_one/2`):

```elixir
defp apply_xp(user_id, result, scores) do
  won? = win_from_result?(result)
  team_score = team_score_for(result, scores)         # tolerant of atom/string keys
  delta = Progression.xp_for_game(team_score, won?)
  {:ok, _profile} = get_or_create_profile(user_id)

  # Increment XP, then recompute the level cache from the new total in the same
  # row update (re-read the incremented value, or compute inline). Two-step:
  # inc xp, then set level = level_for_xp(new_xp).
  from(p in PlayerProfile, where: p.user_id == ^user_id)
  |> Repo.update_all(inc: [veteran_xp: delta])

  new_xp = Repo.one(from p in PlayerProfile, where: p.user_id == ^user_id, select: p.veteran_xp)

  from(p in PlayerProfile, where: p.user_id == ^user_id)
  |> Repo.update_all(set: [veteran_level: Progression.level_for_xp(new_xp)])
  :ok
end

# team_score_for/2: read scores[result.team], tolerating atom/string keys on both
# the result map and the scores map; default 0 if absent.
```

- Both writes run **inside the existing `save_completed_game/4` transaction**
  (same as `apply_one/2`). The XP `inc` is commutative/idempotent-on-replay; the
  level `set` is a pure function of the post-inc XP. (A single `update_all` with
  a SQL expression that re-reads `veteran_xp` for the level is possible but the
  two-step read-then-set is clearer and stays inside the txn; the row is already
  locked by the surrounding transaction's writes.)

## Rebuild change

`rebuild_from_history/1` recomputes `veteran_xp` as the commutative per-game sum
and `veteran_level` from it — order-agnostic, idempotent, mirroring the
counters. Each game's contribution reuses the existing `won_game?/2` (win bonus)
plus the game's `final_scores` (string-keyed JSONB) and the user's team:

```elixir
def rebuild_from_history(user_id) do
  games = from(gs in GameStats, where: ^user_id in gs.player_ids) |> Repo.all()

  games_played = length(games)
  wins = Enum.count(games, &won_game?(&1, user_id))
  losses = games_played - wins

  veteran_xp =
    Enum.reduce(games, 0, fn game, acc ->
      acc + xp_for_history_game(game, user_id)
    end)

  with {:ok, profile} <- get_or_create_profile(user_id) do
    profile
    |> PlayerProfile.changeset(%{
      games_played: games_played,
      wins: wins,
      losses: losses,
      veteran_xp: veteran_xp,
      veteran_level: Progression.level_for_xp(veteran_xp)
    })
    |> Repo.update()
  end
end

# xp_for_history_game/2: team = team for this user (from player_results, with the
# player_ids→position→team fallback get_player_position/2 already provides);
# team_score = game.final_scores[team] (string-keyed JSONB tolerant, default 0);
# won? = won_game?(game, user_id); Progression.xp_for_game(team_score, won?).
```

- `rebuild_all/0` rides along for free.
- `final_scores` is read tolerantly (atom OR string keys; default `0` for legacy
  rows missing a team's score) so the rebuild never crashes on old data — it
  just credits `0 + bonus` where scores are absent, documented as the legacy-row
  floor.
- **Parity is exact** because live and rebuild call the *same* `xp_for_game/2`
  with the same team score + win flag, and XP is a plain sum.
